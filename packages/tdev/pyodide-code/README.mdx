## Ausgabe löschen

`os.system('clear')` und `os.system('cls')` löschen die bisherige Ausgabe des aktuellen Editors. Nachfolgende Ausgaben erscheinen wieder im leeren Logfenster. Beide Befehle geben `0` zurück. Diese Unterstützung gilt für die beiden Löschbefehle; eine allgemeine Betriebssystem-Shell steht im Browser nicht zur Verfügung.

```py live_pyo hideWarning title=Ausgabe_löschen
from os import system
from time import sleep

for i in range(5):
    system('clear')
    print(i)
    sleep(1)
```

Es ist immer nur die aktuelle Ausgabe sichtbar.

## Fibonacci
```py live_pyo id=d5d60431-5589-4d38-9c8c-9b563194f5cc title=Fibonacci_ohne_Rekursion
def fibonacci(n):
    if n <= 0:
        return []
    elif n == 1:
        return [0]
    elif n == 2:
        return [0, 1]
    else:
        seq = [0, 1]
        for i in range(2, n):
            seq.append(seq[-1] + seq[-2])
        return seq
n = int(input("fib von? "))
print(fibonacci(n))
```

### Mit Memoization

```py live_pyo id=22b0f649-9b77-4e97-9ccb-cfeb159bbde9 title=Fibonacci_mit_Memoization
from functools import lru_cache

@lru_cache
def fibonacci(n):
    if n in {0, 1}:
        return n
    return fibonacci(n-1) + fibonacci(n-2)

for n in range(1, 200):
    print(f"Fibonacci({n}) = {fibonacci(n)}")
```

## Python-Pakete laden

Imports werden mit Pythons AST ausgewertet, auch innerhalb von Funktionen oder zusammen mit weiteren Anweisungen auf einer Zeile. Pakete aus der Pyodide-Distribution werden mit deren eingebautem Loader geladen. Bereits verfügbare Module, die Standardbibliothek und lokale JavaScript-Module lösen keine zusätzlichen PyPI-Installationen aus. Fehlgeschlagene Installationen werden im Editor angezeigt.

Für zusätzliche oder versionierte Abhängigkeiten kann die `Pyodide`-Komponente eine Liste von Paketanforderungen erhalten:

Fortschrittsmeldungen beim Laden von Paketen erscheinen ausschliesslich in der Entwicklerkonsole des Browsers. Fehlgeschlagene Installationen werden weiterhin im Editor angezeigt.

## Freie Worker wiederverwenden

Nacheinander gestartete Skripte verwenden einen freien Worker desselben Browser-Tabs wieder. Dadurch bleiben bereits installierte Pakete und importierte Bibliotheken verfügbar. Gleichzeitig laufende Skripte erhalten jeweils einen eigenen Worker. Pro Tab bleiben höchstens zwei freie Worker erhalten; verschiedene Tabs teilen keinen Python-Interpreter.

Python-Fehler behalten den geladenen Worker beim jeweiligen Editor. Beim nächsten Start wird derselbe Worker wiederverwendet.

**Abbrechen** beendet den Worker sofort und initialisiert einen Ersatz. Das gilt auch beim Abbrechen einer Eingabe und stoppt Endlosschleifen zuverlässig. Andere gleichzeitig laufende Skripte behalten ihre Worker. Das abgebrochene Skript wird nicht automatisch erneut ausgeführt; seine Pakete müssen beim nächsten Start erneut geladen werden.

Skriptvariablen werden bei jeder Ausführung neu angelegt. Importierte Module, Dateien, das Arbeitsverzeichnis und anderer Interpreterzustand können zwischen Editoren erhalten bleiben. Worker mit noch laufenden asyncio-Tasks bleiben ebenfalls beim jeweiligen Editor. Erweiterungen müssen geplante asyncio-Callbacks und JavaScript-Timer vor Ende des Skripts selbst beenden; solche Hintergrundaktivitäten werden durch die Task-Prüfung nicht erkannt. Ein ausgefallener Worker wird beim nächsten Start eines Skripts ersetzt.

### Cookie-Klicker: Browser-Ereignisse in Python

`@on_click(cookie)` registriert einen Handler für genau diesen Cookie. Der Handler erhält ein Ereignis mit `type`, `extension`, `target_id`, `timestamp` und `payload`. `await run()` hält das Programm aktiv, bis `webio.stop()` aufgerufen oder im Editor **Abbrechen** gedrückt wird.

Der Store verwaltet für jede `cookieId` ein eigenes MobX-Modell. Mehrere Cookies können unabhängig gesteuert werden; mehrere Ansichten derselben ID teilen dasselbe Modell.

<CodeShowcase lang="md" imports={[`import CookieComponent from '@tdev-components/CookieComponent';`]}>
<CookieComponent cookieId="cookie-demo" />
<CookieComponent cookieId="cookie-zwei" />

```py live_pyo id=62007a34-9647-4c62-83bd-7a0f829e502a title=Cookie_Klicker
from random import randint
from cookie_klicker import use_cookie
from webio import on_click, run

cookie = use_cookie('cookie-demo')
zweiter_cookie = use_cookie('cookie-zwei')

@on_click(cookie)
def drehen(event):
    cookie.set_rotation(cookie.rotation + randint(0, 360))

@on_click(zweiter_cookie)
def schrittweise_drehen(event):
    zweiter_cookie.set_rotation(zweiter_cookie.rotation + 30)

await run()
```
</CodeShowcase>

Der Cookie wird anklickbar, sobald das Programm seine Ereignisquellen angemeldet hat. Eine Ziel-ID kann gleichzeitig nur von einem laufenden Programm für Ereignisse verwendet werden. Ein zweiter Controller erhält eine Fehlermeldung. Nach Ende oder Abbruch werden die Zuordnungen entfernt; alte Klicks werden nicht an einen Neustart weitergegeben.

`use_cookie(id)` liefert innerhalb derselben Ausführung denselben Handle zurück. Seine lokale `rotation` beginnt bei null; `set_rotation()` normalisiert den Winkel auf `[0, 360)` und aktualisiert das Browser-Modell. Ein neuer Handle verändert die bisherige Anzeige erst mit seinem ersten Update.

Handler laufen nacheinander. Für absichtliche Wartezeiten kann ein Handler `async def` verwenden und `await asyncio.sleep(0.1)` aufrufen. Währenddessen können weitere Klicks empfangen werden; ihre Handler starten nach Abschluss des aktuellen Handlers. `time.sleep()`, synchrone Eingaben mit `input()` und lange Berechnungen blockieren dagegen den Empfang im Worker.

Für weitere Ereignistypen steht `@on_event('typ', source=cookie.events)` zur Verfügung. `webio.stop()` beendet den Empfang nach dem aktuellen Handler. Pro Ausführung ist ein `run()`-Aufruf vorgesehen; bei einem Handler-Fehler wird das Programm mit einer Diagnose beendet. Überfüllte Ereigniswarteschlangen beenden die betroffene Ausführung ebenfalls mit einer Fehlermeldung.

### Erweiterungen registrieren

Eine Erweiterung hat zwei getrennte Einstiegspunkte: `worker.ts` stellt Python-Module bereit, `client.ts` verarbeitet deren Nachrichten im Browser. Beide verwenden denselben Payload-Typ aus `protocol.ts`. React-Komponenten und MobX-Stores bleiben normale Bestandteile der Website.

Die Einstiegspunkte werden explizit im bestehenden Pyodide-Plugin konfiguriert:

```ts title="siteConfig.ts"
import type { PluginOptions } from '@tdev/pyodide-code/plugin';

plugins: [
    [
        require.resolve('@tdev/pyodide-code/plugin'),
        {
            extensions: [
                {
                    name: 'clock',
                    worker: require.resolve('./website/pyodide/clock/worker'),
                    client: require.resolve('./website/pyodide/clock/client')
                }
            ]
        } satisfies PluginOptions
    ]
]
```

Die Namen der Erweiterungen müssen eindeutig sein. `require.resolve()` liefert absolute Dateipfade; relative Einstiegspfade in den Optionen werden relativ zum Docusaurus-Seitenverzeichnis aufgelöst. Die Konfiguration enthält nur Dateipfade und Namen, keine React-Komponenten oder Store-Instanzen. Nach Änderungen an der Erweiterungsliste muss der Entwicklungsserver neu gestartet werden.

Das Plugin erzeugt getrennte Registries für Worker und Browser. Es braucht weder ein Alias-Override von Package-Dateien noch eine globale Registrierung beim App-Start. `worker.ts` darf keine React-, DOM- oder Store-Abhängigkeiten importieren; gemeinsame Payload-Typen werden mit `import type` eingebunden.

Beim Laden der jeweiligen Registry wird einmalig geprüft, ob die Worker-Einträge `createModules()` und die Browser-Einträge `handleMessage()` bereitstellen. Ein ungültiger Export verhindert die Initialisierung dieser Registry; die Fehlermeldung nennt die Erweiterung und den betroffenen Einstiegspunkt.

### Uhr: gemeinsamer Vertrag

```ts title="website/pyodide/clock/protocol.ts"
export interface ClockTime {
    hours: number;
    minutes: number;
    seconds: number;
}

export type ClockUpdate = Partial<ClockTime>;
```

Alle Winkel sind in Grad angegeben. Eine Nachricht kann einzelne Zeiger oder die ganze Uhr ändern. Die beiden Einstiegspunkte verwenden `ClockUpdate` als Typparameter. Die Typen prüfen den selbst geschriebenen Worker und Handler, es gibt keine automatische Laufzeitvalidierung des Payloads.

### Uhr: Python-Modul im Worker

    {clockWorkerSource}

`defineWorkerExtension<Payload>()` erhält eine Factory. Diese liefert ein Objekt, dessen Schlüssel die Python-Modulnamen sind, hier `clock`. Eine Erweiterung kann mehrere Module bereitstellen; Modulnamen und Nachrichtentypen sind unabhängig voneinander. Doppelte Modulnamen und der interne Name `browser_input` werden mit einer Fehlermeldung abgelehnt.

Der Factory-Kontext bietet:

- `editorId`: die ID des ausführenden Editors.
- `send(targetId, payload)`: sendet eine Nachricht an den Browser-Handler dieser Erweiterung. Das Framework ergänzt Editor-ID, Erweiterungsname und Zeitstempel. Der Payload muss durch strukturiertes Klonen übertragbar sein, beispielsweise ein Objekt aus Zahlen, Strings und Arrays.
- `events.source(targetId)`: erzeugt einen Ereignisquellen-Deskriptor, der an die aktuelle Ausführung gebunden ist. Ein Python-Handle kann ihn als `events` bereitstellen. `webio.run()` meldet die Quellen seiner registrierten Handler an; ein Browser-Store sendet Ereignisse mit `pyodideStore.events.emit(source, { type, payload })` an den aktiven Controller.

Die Factory wird bei **jeder Ausführung** aufgerufen und ihre Module werden vor dem Python-Code registriert. Damit funktionieren auch dynamische Imports wie `importlib.import_module('clock')`. Der Worker wartet vor Abschluss auf ausstehende Nachrichten an die Browser-Handler. Ein Handler-Fehler wird als Ausführungsfehler im Editor angezeigt. Bereits zugestellte Änderungen werden nicht zurückgerollt.

Schlagen sowohl die Ausführung als auch deren Abschluss fehl, erscheint der ursprüngliche Ausführungsfehler zuerst. Zusätzliche Fehler beim Zustellen von Nachrichten oder beim Aufräumen werden darunter angezeigt. Die weiteren Aufräumschritte werden auch nach einem Fehler ausgeführt.

`defineClientExtension<Payload>()` erhält einen synchronen Handler. Der Kontext enthält den aktuellen `root`-Store. Die Nachricht enthält `editorId`, `targetId`, `timeStamp` und `payload`. Der Handler läuft innerhalb einer MobX-Action; er aktualisiert die bestehenden Website-Stores.

Die Uhr verwendet weiterhin den [ClockStore](https://github.com/GBSL-Informatik/teaching-dev/blob/main/tdev-website/website/stores/ClockStore.ts), das [Clock-Modell](https://github.com/GBSL-Informatik/teaching-dev/blob/main/tdev-website/website/packages/pyodide-code/models/Clock.ts) und die [React-Komponente](https://github.com/GBSL-Informatik/teaching-dev/blob/main/tdev-website/website/packages/pyodide-code/components/Clock/index.tsx). Nur der Store muss im `SiteStore` vorhanden sein; ein `handleMessage`-Override ist nicht nötig. Die Komponente kann wie bisher unabhängig vom Editor im MDX platziert werden:

```mdx
import Clock from '@tdev/packages/pyodide-code/components/Clock';

<Clock clockId="sbb-uhr" />
```

Python verwendet weiterhin `from clock import use_clock` und dieselbe Ziel-ID. Mehrere Komponenten oder Editoren können absichtlich dieselbe Ziel-ID verwenden; die Ziel-IDs gelten für den gemeinsamen Website-Store, nicht nur für einen Editor.

### Zustand und Lebensdauer

Die Browser-Stores gehören weiterhin der Website und leben mit deren Root-Store. Der Zustand der Uhr bleibt nach Ende oder Abbruch eines Skripts erhalten; ein Neustart setzt ihn nicht automatisch zurück. Ein unbekanntes Ziel wird beim ersten Update im `ClockStore` angelegt, auch wenn noch keine React-Komponente dafür angezeigt wird.

Jeder Aufruf von `use_clock()` erzeugt einen eigenen Python-Handle mit zunächst lokalen Nullwerten. Seine Getter lesen die letzten Werte dieses Handles, nicht den Browser-Store und nicht andere Handles. `set_seconds()` ändert im Browser nur den Sekundenzeiger. `reset()` setzt alle Zeiger zurück. Diese Erweiterung bietet keine Rückfragen vom Browser an Python.

Worker können zwischen Editoren wiederverwendet werden. Die registrierten JavaScript-Module erhalten pro Ausführung einen neuen Kontext. Bereits importierte Python-Hilfsmodule können jedoch alte Referenzen auf Module oder Handles behalten; deren Cache wird nicht rekursiv geleert. Solche Hilfsmodule sollen das Modul oder die Factory innerhalb der pro Ausführung aufgerufenen Funktion neu importieren und erst dann Handles anfordern. Ein auf Modulebene gespeichertes `from clock import use_clock` bleibt sonst an den alten, bereits geschlossenen Kontext gebunden.

Erweiterungen müssen eigene Timer und Hintergrundaufgaben vor Ende des Skripts beenden. Nachrichten nach Abschluss werden verworfen. **Abbrechen** beendet den Worker; ausstehende Nachrichten einer abgebrochenen oder ersetzten Ausführung werden durch die bestehende Ausführungsprüfung ignoriert. Das Framework stellt keine automatische Ressourcenverwaltung oder Hintergrunddienste für Erweiterungen bereit.

## Pyodide-Version konfigurieren

Die exakte `pyodide`-Abhängigkeit in `package.json` legt die Laufzeitversion fest.
`config.ts` leitet daraus `PYODIDE_VERSION` und `PYODIDE_INDEX_URL` ab. Worker und
Main-Thread-Hook verwenden denselben ES-Modul-Loader und dieselbe CDN-Adresse.
Das Docusaurus-Plugin prüft beim Start, dass die Version exakt angegeben ist,
und konfiguriert den für Pyodide erforderlichen Modul-Worker.

Zum Aktualisieren auf eine neue stabile Version:

```bash
yarn workspace @tdev/pyodide-code add pyodide@<version> --exact
```

Die geänderten Dateien `package.json` und `yarn.lock` müssen gemeinsam übernommen werden.

### Docusaurus- und Rspack-Updates prüfen

Der `ModuleWorker`-Konstruktor, der Chunk-Name `pyodide-worker` und die Parser- und
SplitChunks-Konfiguration in `plugin.ts` gehören zusammen. Sie erhalten den
ES-Modul-Worker und verhindern gemeinsame Chunks, die Rspack sonst über
`importScripts()` laden würde. Nach Updates von Docusaurus, Rspack oder Pyodide
muss ein Produktions-Build im Browser geprüft werden: Der Worker muss als Modul
starten und Python einschliesslich Paketimporten und Eingaben ausführen können.
